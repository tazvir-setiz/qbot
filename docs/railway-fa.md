# راهنمای فارسی راه‌اندازی ربات روی Railway

مبنای این راهنما: همین پروژه، ورودی `main.py`، SQLite و دریافت پیام با polling. تاریخ بررسی مستندات: ۲۷ سپتامبر ۲۰۲۶. نام یا جای گزینه‌ها ممکن است با تغییر رابط Railway کمی متفاوت باشد.

## ۱. قبل از شروع

این ربات یک پردازش دائمی است؛ وب‌سایت یا سرویس HTTP نیست. به دامنه، بازکردن پورت، متغیر `PORT` و webhook احتیاج ندارد. پنل مدیریت آن داخل تلگرام است.

آماده داشته باشید:

- حساب Railway با امکان اجرای سرویس دائمی و Volume؛ اعتبار و هزینهٔ حساب را در پنل خود بررسی کنید. این راهنما رایگان‌بودن اجرای دائمی را فرض نمی‌کند.
- مخزن GitHub پروژه، ترجیحاً خصوصی، با فایل‌های جدید این راهنما.
- توکن بات از BotFather و یک رمز مدیریت مناسب.
- گروه مقصد و امکان اضافه‌کردن بات به آن.

اگر همین توکن روی رایانه، cPanel یا سرویس دیگری اجرا می‌شود، پیش از فعال‌کردن نسخهٔ Railway آن را متوقف کنید. فقط یک نمونهٔ polling با این توکن اجرا شود.

## ۲. فایل‌های آمادهٔ پروژه

| فایل | کاربرد |
| --- | --- |
| `Dockerfile` | ساخت محیط Python 3.12 و نصب وابستگی‌ها |
| `railway.json` | تعیین Dockerfile، فرمان اجرا و سیاست راه‌اندازی مجدد |
| `.dockerignore` | خارج‌کردن رمزها و دیتابیس محلی از فرایند ساخت |
| `.env.example` | فهرست تنظیمات؛ مقادیر نمونه قابل استفاده نیستند |
| `scripts/backup_db.py` | ساخت نسخهٔ سازگار پشتیبان از SQLite |

فایل `.env`، دیتابیس واقعی و پوشهٔ `.venv` را در GitHub قرار ندهید. محیط ویندوز را روی سرور کپی نکنید؛ Docker وابستگی‌ها را نصب می‌کند. ورودی درست پروژه `main.py` است.

## ۳. ساخت پروژه و سرویس

۱. در Railway پروژهٔ جدید بسازید و گزینهٔ اتصال به GitHub Repository را انتخاب کنید.
۲. دسترسی همان مخزن را بدهید و شاخهٔ موردنظر را انتخاب کنید.
۳. ریشهٔ سرویس را پوشه‌ای تعیین کنید که `Dockerfile`، `main.py` و `railway.json` در آن هستند؛ اگر پروژه در ریشهٔ مخزن است، مسیر زیرپوشه نگذارید.
۴. اگر پیش از تکمیل Variables استقرار خودکار آغاز شد و خطای تنظیمات گرفت، طبیعی است؛ ابتدا مراحل بعدی را کامل و سپس Deploy کنید.
۵. در جزئیات Build بررسی کنید Dockerfile استفاده شده باشد. فرمان اجرای این پروژه `python -u main.py` است.

تنظیمات فایل `railway.json` بر تنظیمات متناظر داشبورد اولویت دارند؛ تغییر فرمان در داشبورد به‌تنهایی الزاماً مؤثر نیست. [مرجع Config as Code](https://docs.railway.com/config-as-code/reference)

## ۴. ساخت دیسک پایدار؛ مرحلهٔ ضروری

۱. برای همین سرویس یک Volume بسازید یا متصل کنید.
۲. Mount Path را دقیقاً `/data` قرار دهید.
۳. در Variables مقدار `DB_PATH` را `/data/bot_data.db` بگذارید.
۴. Volume باید به همان سرویس بات متصل باشد، نه به سرویس دیگر پروژه.

اگر دیتابیس داخل `/app` بماند، فایل کانتینر جایگزین دیسک پایدار نیست و تنظیمات ممکن است با استقرار جدید از بین بروند. Volume هنگام اجرای سرویس متصل می‌شود؛ ساخت دیتابیس را به Build یا Pre-deploy منتقل نکنید. خود برنامه هنگام اجرا جدول‌ها را ایجاد یا به‌روزرسانی می‌کند. [مستندات Volume](https://docs.railway.com/volumes)

## ۵. تنظیم Variables

در بخش Variables سرویس، متغیرها را تک‌به‌تک وارد کنید. مقدار واقعی توکن و رمز را فقط در همین پنل نگه دارید؛ کوتیشن اطراف مقادیر وارد نکنید.

| نام | مقدار یا راهنما |
| --- | --- |
| `BOT_TOKEN` | توکن واقعی BotFather |
| `ADMIN_PASSWORD` | رمز ورود پنل ربات |
| `TIMEZONE` | `Asia/Tehran` |
| `DB_PATH` | `/data/bot_data.db` |
| `SURAH_LIST_FILE` | `surah_list.txt` |
| `LOG_LEVEL` | `INFO` |
| `ADMIN_USER_IDS` | اختیاری؛ شناسهٔ عددی مدیران با کاما، مثل `123456789,987654321` |
| `GROUP_ID` | اختیاری؛ بهتر است خالی بماند و مقصد با `/group` انتخاب شود |

`ADMIN_USER_IDS` نام کاربری نیست. اگر شناسهٔ اشتباه وارد کنید، ربات به درخواست آن کاربر پاسخ مدیریت نمی‌دهد. خالی‌بودن آن یعنی هر فرد با رمز صحیح می‌تواند وارد شود.

متغیر محیط سیستم بر `.env` اولویت دارد. در Railway نیازی به آپلود `.env` ندارید.

## ۶. تنظیم اجرای دائمی

- تعداد replica را **۱** و اجرا را در **یک منطقه** نگه دارید.
- Serverless / Sleep را غیرفعال نگه دارید؛ این برنامه باید برای دریافت پیام و زمان‌بندی روشن بماند. [مستندات Serverless](https://docs.railway.com/deployments/serverless)
- Healthcheck Path را خالی بگذارید؛ این ربات مسیر HTTP مانند `/health` ندارد.
- Cron Schedule را برای سرویس Railway تنظیم نکنید؛ برنامه خودش زمان‌بندی را اجرا می‌کند.
- فایل آماده سیاست `ON_FAILURE` با حداکثر ۱۰ تلاش مجدد دارد. پایان عادی پردازش لزوماً باعث ری‌استارت نمی‌شود؛ در صورت توقف، لاگ را بررسی و بعد Restart کنید.
- فایل آماده هم‌پوشانی را صفر و فرصت توقف را ۳۰ ثانیه تعیین می‌کند. هنگام جابه‌جایی deployment، همچنان مراقب اجرای هم‌زمان نسخهٔ قبلی باشید؛ برای تغییر حساس ابتدا نسخهٔ قبلی را متوقف کنید. [چرخهٔ توقف Railway](https://docs.railway.com/deployments/deployment-teardown)

برای این worker نیازی به Generate Domain ندارید. نبود صفحهٔ وب نشانهٔ خرابی بات نیست.

## ۷. Deploy و راه‌اندازی داخل تلگرام

۱. تغییرات سرویس را Deploy کنید.
۲. Build Logs باید نصب وابستگی‌ها را بدون خطا نشان دهد.
۳. در Runtime Logs پیام `Bot initialized` و شروع برنامه را بررسی کنید. خطای `Conflict` یعنی نسخهٔ دیگری با همین توکن روشن است.
۴. در گفت‌وگوی خصوصی بات `/start` را بزنید و رمز را وارد کنید.
۵. بات را به گروه اضافه کنید و اجازهٔ ارسال متن بدهید.
۶. `/group` ← «انتخاب گروه» ← گروه مقصد را انتخاب کنید.
۷. «بررسی دسترسی» و سپس «ارسال آزمایشی» را بزنید؛ دومی واقعاً یک پیام به گروه می‌فرستد.
۸. سوره/صفحه، دوره و ساعت اولین ارسال را تنظیم کنید؛ «شروع ارسال» را بزنید.
۹. زمان ارسال بعدی در پنل را بررسی کنید. شروع برنامه الزاماً به معنی ارسال همان لحظه نیست؛ اگر ساعت امروز گذشته باشد، اولین نوبت معمولاً فرداست.

برای آزمون اولیه ساعت را چند دقیقه جلوتر و دوره را مثلاً یک ساعت بگذارید. پس از مشاهدهٔ پیام، تنظیمات نهایی را اعمال کنید.

## ۸. نگهداری اطلاعات، پشتیبان و انتقال

در بخش Volume، گزینه‌های backup دستی/زمان‌بندی‌شدهٔ حساب را بررسی کنید. نسخهٔ پشتیبان فقط داخل همان دیسک، جای پشتیبان مستقل را نمی‌گیرد. [پشتیبان Volume](https://docs.railway.com/volumes/backups)

در پوستهٔ **داخل کانتینر مستقر** می‌توانید اجرا کنید:

```bash
python scripts/backup_db.py /data/backups/bot-before-update.db
```

نام خروجی باید جدید باشد؛ ابزار فایل موجود را بازنویسی نمی‌کند. برای دسترسی به پوسته از قابلیت SSH سرویس/CLI Railway استفاده کنید. `railway run` روی رایانهٔ خودتان، به‌تنهایی پوستهٔ کانتینر یا دسترسی به Volume ایجاد نمی‌کند. [Railway SSH](https://docs.railway.com/cli/ssh)

اگر حفظ اطلاعات نسخهٔ محلی لازم است:

۱. ارسال و فرایند نسخهٔ قدیمی را متوقف کنید.
۲. با `scripts/backup_db.py` یک snapshot بسازید؛ هنگام روشن‌بودن SQLite فایل `.db` را جدا از WAL کپی نکنید.
۳. snapshot و همان نسخهٔ `surah_list.txt` را حفظ کنید؛ شناسهٔ سوره‌ها به ترتیب فایل وابسته است.
۴. پیش از فعال‌شدن بات روی Railway، از روش انتقال فایل پشتیبانی‌شده در دسترسی خود، snapshot را به Volume و مسیر `/data/bot_data.db` منتقل کنید. این راهنما فرمان انتقال فرضی برای همهٔ حساب‌ها ارائه نمی‌کند؛ دسترسی SSH/ابزار انتقال شما باید واقعاً Volume را ببیند.
۵. فایل موجود را فقط پس از گرفتن پشتیبان و توقف کامل writer جایگزین کنید. راه ساده‌تر برای راه‌اندازی جدید، دیتابیس خالی و تنظیم دوباره از تلگرام است.

پس از Restart، گروه و پیشرفت باید باقی مانده باشند، ولی ورود با رمز دوباره لازم است. اگر نتیجهٔ ارسال قبلی نامشخص اعلام شد، ابتدا آخرین پیام گروه را بررسی و سپس صفحهٔ صحیح را انتخاب کنید.

## ۹. به‌روزرسانی و بازگشت

قبل از تغییر کد یا فهرست سوره‌ها پشتیبان بگیرید. کد جدید را به شاخهٔ متصل push و وضعیت deployment را بررسی کنید. برگشت به deployment قدیمی لزوماً دیتابیس را برنمی‌گرداند؛ تغییرات ساختار دیتابیس و کد باید سازگار باشند. برای خاموش‌کردن دائمی، deployment را متوقف و استقرار خودکار بعدی را هم مدیریت کنید؛ دکمهٔ «توقف ارسال» داخل بات فقط برنامهٔ روزانه را متوقف می‌کند.

## ۱۰. عیب‌یابی

| نشانه | اقدام |
| --- | --- |
| `Missing required setting` | Variables توکن و رمز و نام دقیق آن‌ها را بررسی و Deploy کنید |
| `Conflict` | نسخهٔ محلی، سرویس دوم و deployment قبلی را بررسی کنید |
| `Chat not found` | از `/group` گروه را دوباره انتخاب کنید؛ بات باید عضو باشد |
| تنظیمات پس از deploy پاک می‌شود | اتصال Volume و `DB_PATH=/data/bot_data.db` را بررسی کنید |
| `unable to open database file` | مسیر و امکان نوشتن روی Volume را بررسی کنید |
| سرویس روشن است ولی پیام نمی‌آید | وضعیت «فعال»، ارسال بعدی و آخرین خطای پنل را بررسی کنید |
| `Application failed to respond` در آدرس وب | این پروژه HTTP ندارد؛ بررسی سلامت را از لاگ و تلگرام انجام دهید |
| تست ارسال موفق است ولی عکس نمی‌رود | مجوز رسانه با مجوز متن فرق دارد؛ تنظیمات گروه را بررسی کنید |

فایل‌ها برای استقرار آماده شده‌اند؛ ساخت Docker و استقرار واقعی Railway باید در محیط میزبان انجام و بررسی شوند.
